Section 1  Product Vision & Overview

Product Vision

PolyVerses is an AI-native product management workbench — an orchestrated multi-agent workspace for product teams to discover, plan, build, and govern products with AI assistance at every layer.

The Bet

Product management is information-heavy, decision-rich, and chronically under-automated. A mesh of specialized AI agents — each with a clear role, system prompt, and outputs — can amplify PM capacity without replacing human judgment. The orchestrator routes tasks; the human approves decisions.

Current State

Phase 0 foundation complete: 23-agent orchestration mesh, React 19 + Vite 6 + Tailwind 4 frontend, Express server with Gemini 3.5, Firebase Auth + Firestore, full observability dashboard, human-in-the-loop gates, prompt console, code browser. The system is functional but domain-agnostic — it needs a concrete product context to demonstrate value.

Product Principles

  • Agentic, not chatty. Each agent has a defined role, inputs, outputs, and system prompt — not a general chat interface.
  • Human-in-the-loop by default. No agent writes back to shared state without a human gate. The 15-minute undo window and RBAC are non-negotiable.
  • Observability woven in. Every agent action is logged, typed, and visible. You can see which agent produced which output and why.
  • Token budget discipline. Small models for classification/retrieval, capable models for synthesis — and the system knows the difference.
  • Progressive disclosure. The platform surfaces what's needed when it's needed — the prompt console, code browser, and observability dashboard are on-demand, not in the critical path.

Target Users

  • Product Managers — primary operator. Uses orchestration console, prompt console, workflow execution, observability.
  • Product Leaders (CPO/VP) — oversight via RBAC, governance layer, strategic portfolio view.
  • Engineers — consume agent outputs (specs, user stories, code samples) from the code browser.
  • Product Ops — maintains the agent network, system prompts, and workflow definitions.

Section 2  Architecture Principles & Decisions

Design Principles

  1. Server-side AI, client-side UX. The Gemini API key never leaves the server. The client calls the app's own API endpoints — never Gemini directly. Enforced by architecture, not convention.
  2. Agent-oriented, not model-oriented. The system is organized around agents with roles, not around LLM calls. Each agent has a system prompt, input schema, output schema, and constraints. The orchestrator routes between them.
  3. Code-as-configuration for agents. System prompts, agent definitions, and sample code live in TypeScript files — editable, version-controlled, inspectable via the prompt console and code browser.
  4. Human judgment is the execution layer. Agents propose; humans dispose. The compliance gate, 15-minute undo window, and RBAC are the enforcement mechanisms.
  5. Observability is not an afterthought. Every agent action is logged with agentId, timestamp, status, confidence score, and output. The D3 topology + heatmap and observability dashboard make the system legible.
  6. Progressive disclosure for power tools. The orchestration console, prompt console, and code browser are available but not in the critical path for everyday use.

Token Budget Philosophy

The system uses Gemini 3.5 Flash as the default model for all agents. Flash provides strong capability at low cost — appropriate for the classification, summarization, structuring, and light reasoning tasks that dominate PM work. For tasks requiring deeper reasoning (complex opportunity analysis, multi-criteria prioritization with trade-offs), the system is designed to route to a higher-capability model, but this is not yet wired. The principle: use the cheapest model that does the job acceptably, and log token usage per agent so the team can see where money goes.

What the Architecture Inherits from PolyVerses

The PolyVerses architecture is the core platform. PolySync (the fitness coach variant documented in docs/06-second-brain-architecture.md) inherits: the 23-agent orchestration pattern (refactored to 12 fitness agents), agent network D3 visualization, observability dashboard, human-in-the-loop gates, prompt console, code browser, RBAC, Firebase Auth + Firestore, server-side Gemini, and CI pipeline. The domain logic changes; the infrastructure is reusable. The architecture reference (2,389 lines) documents both the PM workbench domain and the fitness domain adaptation.

3.5 Data Lifecycle & Privacy

  • Profile — created on onboarding, updated on edit, read by all agents that need user context.
  • Workouts — written on completion, read by F05 (adaptation), F04 (recovery), F06 (chat context), progress dashboard.
  • Plans — written by F02 (generation + adaptation), read by client (weekly plan view, today's workout), F05 (adaptation source).
  • Wearable data — written by F10 (webhooks), read by F04 (recovery), F06 (chat context). Gated by healthDataConsent — Firestore rules and API-level check.
  • Chat sessions — written by F06 (append messages), read by F06 (context continuity).
  • Check-ins — written by client (post-workout/daily), read by F09 (sentiment/dropout risk), F04 (recovery input).
  • Retention — all collections use serverTimestamp() for createdAt/updatedAt. Immutable fields (createdAt, workout logs) protected from client modification.
  • Deletion — GDPR/CCPA pipeline via Firebase Admin SDK (designed, not implemented). Data export as CSV/JSON (planned).

5.1 API Overview

  • Base URL: http://localhost:3000 (dev) / production server URL

  • Content-Type: application/json request and response.
  • Error format: { error: string } with appropriate HTTP status.

  • Sandbox fallback: If !ai (key missing or invalid), endpoints return deterministic/sandbox responses.

7.3 Token Budget Governance (Design — Not Implemented)

The architecture document (docs/06-second-brain-architecture.md Section 11) designs a governance layer that wraps the existing agent mesh. Key elements:

  • Per-session token budget: 200K tokens per user session; circuit breakers trip at 80% (small), 95% (medium), 100% (capable model blocked).
  • Per-agent token caps: F02 (plan generation) capped at 15K/turn; F06 (chat) at 12K/turn; F04 (recovery) at 2K; F01/F03/F07/F09/F10 at 1K.
  • Model-tier routing: Flash for standard agents; Flash Thinking for F02/F04/F05; Pro for F06 only.
  • Context cache: LRU cache for assembled context — 24h TTL, 100 entries max — so repeated questions don't re-fetch profile + plan + workouts.
  • Scheduled distillation: Weekly batch — Level 2 (gist) summaries of chat sessions + check-ins + workout patterns. Monthly Level 3 (summary). Quarterly Level 4 (principle extraction).
  • Observability endpoint: GET /api/governance/usage — session token usage, weekly distillation count, circuit breaker state per agent, cache hit rate.

This governance layer is designed but not implemented. It's the bridge between "agents work" and "agents work within budget."

7.4 Data Governance

  • Health Data Consent: API-level gate (F11) + Firestore rules. No wearable data processed without explicit user consent. Data encrypted at rest by Firebase. Not used for model training.
  • GDPR/CCPA: Deletion pipeline via Firebase Admin SDK (designed, not implemented). Data export as CSV/JSON (planned). 30-day deletion SLA.

P5Progressive summarization — Level 1 (verbatim) → Level 2 (gist) → Level 3 (summary) → Level 4 (principle). Distillation runs on a schedule, not per-capture.The Distillation Scheduler runs weekly (default), producing Levels 2/3/4 from Level 1 notes. The summaries are stored on the Note object.

P7Observability is not optional — Every agent run emits a structured observability event: agent ID, model tier, token in/out, duration, decision gate triggered (Y/N), outcome.The Observability Emitter logs every AgentRun to the agent_runs collection and emits an event for the dashboard.
P8Circuit breakers are automatic — Three levels: small (per-agent budget exceeded), medium (session budget exceeded), capable (compliance/quality threshold breached). The capable breaker requires human review.The Circuit Breaker module checks budget thresholds and compliance/quality signals. The capable breaker presents to the PM for review.
P9Assembled-context cache — Similar questions reuse a cached assembled-context (24h TTL, 100-entry LRU). Avoids re-assembling context and re-invoking specialists for repeat queries.The Context Cache checks for a cache hit before re-assembling. Cache hits skip retrieval, assembly, and specialist invocation.
P10Extensible by design — New specialists plug in via the agent registration pattern (name, model tier, system prompt, budget, capabilities). No core code change to add a specialist.The specialist registry (in the orchestrator) accepts new agent definitions. The router uses the registry to select specialists.

11.4 Privacy Strategy

Data minimisationCapture only what is needed for the PM's work. No ambient collection. Voice capture is explicitly started and stopped by the user.
Purpose limitationNotes and contexts are used only for the PM's personal productivity and decision-making — not for model training or third-party sharing.
User controlThe PM can delete any note, any assembled context, any agent run log. Data deletion is a first-class operation (F10 / API endpoint).
PII detectionGuardrails include PII detection before content enters the index or is sent to Gemini. Detection is a placeholder today; it is on the build roadmap.
Encryption at restFirestore encrypts data at rest by default. Gemini API traffic is encrypted in transit (HTTPS).
Access controlFirestore security rules (firestore.rules) restrict each user to their own data. The x-user-id header is verified by auth middleware on every API call.

15.3 Firestore Security Rules

The security rules live in firestore.rules (419 lines). The core rules are:

// firestore.rules — PolyVerses security rules (abridged)

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Helper: get the authenticated user's UID
    function isAuthenticated() {
      return request.auth != null;
    }
    function isOwner() {
      return isAuthenticated() &&
        request.auth.uid == resource.data.userId;
    }
    function isOwnerOnCreate() {
      return isAuthenticated() &&
        request.auth.uid == request.resource.data.userId;
    }

    // Notes: users can read/write their own notes
    match /notes/{noteId} {
      allow read: if isOwner();
      allow write: if isOwnerOnCreate();
      allow delete: if isOwner();
    }

    // Assembled contexts: users can read/write their own
    match /assembled_contexts/{ctxId} {
      allow read: if isOwner();
      allow write: if isOwnerOnCreate();
      allow delete: if isOwner();
    }

    // Agent runs: users can read their own run logs
    match /agent_runs/{runId} {
      allow read: if isOwner();
      allow write: if isOwnerOnCreate();
    }

    // Settings: users can read/write their own
    match /settings/{settingId} {
      allow read: if isOwner();
      allow write: if isOwnerOnCreate();
    }

    // Decision log: users can read/write their own
    match /decision_log/{decId} {
      allow read: if isOwner();
      allow write: if isOwnerOnCreate();
    }

    // Users: users can read/write their own profile
    match /users/{userId} {
      allow read: if isAuthenticated() && request.auth.uid == userId;
      allow write: if isAuthenticated() && request.auth.uid == userId;
    }
  }
}

The rules enforce that every document is owned by a single user (userId field matches the auth UID). A user can only read, write, or delete their own documents. This is the primary authorization boundary.

17.5 Endpoint Details — Key Flows

POST /api/generate-plan — F02 Workout Generator

The flagship endpoint. Generates a weekly workout plan from a fitness profile + the 101-exercise library. Uses Gemini Flash Thinking with a detailed system prompt, with a deterministic fallback if Gemini is unavailable.

Flow: Validate profile exists → load ExerciseLibrary (101 exercises) → call Gemini Flash Thinking with system prompt + profile + exercises → parse JSON response → validate against schema → save plan to Firestore → return plan
System prompt: 700+ words covering exercise science, periodization, injury handling, equipment constraints, intensity management, substitution rules, and output format
Token cost: ~3-5K input tokens (profile + 101 exercises), ~1-2K output tokens (7-day plan with exercises per day)
Deterministic fallback: If Gemini fails or returns invalid JSON, generate a balanced plan using round-robin exercise selection, injury filtering, and equipment matching — no AI, just rules

POST /api/chat — F06 Coaching Chat

The natural-language coaching interface. Uses Gemini Pro with full context (profile + plan + recent workouts + recovery) and a coaching persona system prompt.

Flow: Validate user + profile + plan → load recent workouts + recovery + checkins → build context object → call Gemini Pro with coaching prompt + context + user message → return response
Token cost: ~5-10K input tokens (full context), ~1-3K output tokens (coaching response)
Context: Profile (goals, level, injuries, equipment, schedule), current plan (7 days of workouts), recent workouts (last 2 weeks of logs), recovery score, recent checkins

POST /api/adapt-plan — F05 Plan Adaptor

Adjusts the current plan based on what was completed, skipped, or how the user is feeling. Uses Gemini Flash Thinking with adaptation logic.

Flow: Load current plan → load checkin data (if provided) → load recent workout logs → call Gemini Flash Thinking with adaptation prompt → parse response → save new plan version → return
Token cost: ~2-4K input tokens, ~1-2K output tokens
Triggers: Checkin submission, manual "adapt plan" action, workout completion (if auto-adaptation is enabled)

POST /api/checkin — F04 Recovery Analyst

Collects daily checkin data (sleep, soreness, energy, stress, nutrition, mood, skip/modify) and computes a recovery score. Uses Gemini Flash Thinking if checkin data is provided; otherwise returns a deterministic recovery score.

Flow: Validate checkin data → if Gemini available, call Flash Thinking with recovery prompt + checkin data → parse recovery score → save checkin to Firestore → return checkin + recovery score
Deterministic fallback: If Gemini unavailable, compute recovery score from sleep quality (0-100), soreness level inverted, energy level, with configurable weights
Token cost: ~1-2K input tokens, ~200-500 output tokens (recovery score + brief note)

19.2 Feature Prioritization Framework

Framework: PolyVerses uses a lightweight RICE-inspired prioritization model:
  • Reach — how many users does this affect? (1-10)
  • Impact — how much does it move the key metric? (1-10)
  • Confidence — how sure are we about reach and impact? (50%-100%)
  • Effort — how many person-hours to build? (inverse — lower is better)

Priority score = (Reach × Impact × Confidence) / Effort

The PM adjusts scores qualitatively — the formula is a guide, not a rule. Strategic importance, user pain, and timing can override the score.

21 · Governance

Governance in PolyVerses covers how the system is controlled — token budgets, circuit breakers, the human gate, observability, and the decision audit trail. The governance layer is what keeps the AI agents useful rather than expensive or uncontrolled.

21.1 Governance Principles

#PrincipleWhat it means
G1Budgets are enforced, not advisoryThe system stops when budgets are exceeded. The PM can increase budgets, but the default is to stop.
G2Circuit breakers have three levelsSmall (per-agent budget exceeded — stop that agent), Medium (session budget exceeded — stop all agents for the session), Capable (compliance/quality threshold breached — require human review).
G3Human gate is required for decisionsNo agent writes back a decision-intent output without the PM explicitly approving it. Informational outputs are shown directly.
G4Observability is built-in, not bolted-onEvery agent run emits a structured event. The PM can see what the system did, what it cost, and what it decided.
G5Distillation is scheduled, not per-captureProgressive summarization runs on a weekly cron by default. The PM can trigger it manually or adjust the schedule.
G6Context is cached, not reassembledRepeat queries reuse cached assembled contexts (24h TTL). This saves tokens and improves response time.
G7The PM can audit any decisionThe decision log records every PM decision made through the human gate — what was proposed, what was decided, when, and why.

21.5 Human Gate Design

AspectDesign
TriggerAny agent output classified as "decision-intent" by the Output Gateway. Informational outputs bypass the gate and go straight to the UI.
PresentationThe PM sees the full agent output, the rationale (if provided), the token cost, the sources (if applicable), and a clear "Approve" / "Reject" action.
ApprovalExplicit — the PM clicks "Approve" to commit the decision. The approval is logged in the decision_log collection with the decision text, rationale, agent ID, context hash, and timestamp.
RejectionExplicit — the PM clicks "Reject" to discard the output. The rejection is logged in the decision_log collection. The output is not written back.
Undo window15 minutes from approval. Within the window, the PM can undo the write-back (revert the decision). After 15 minutes, the decision is permanent (until manually edited or deleted).
Override (capable breaker)If a capable circuit breaker blocks an output, the PM sees the reason and can choose to override (with rationale) or dismiss. The override is logged and auditable.
Gate rate monitoringThe observability dashboard shows the decision gate rate — what percentage of agent outputs trigger the gate. A high gate rate may indicate that the Output Gateway classifier needs tuning, or that agents are producing too many decision-intent outputs.

21.7 Distillation Governance

AspectDesign
ScheduleWeekly by default (Sunday 00:00 UTC, configurable). The PM can trigger manual distillation at any time.
ScopeAll Level 1 notes (verbatim_text is set, l2_summary/l3_summary/l4_summary are not) — batched by project + recency. Notes with existing summaries are skipped.
Budget100,000 tokens per weekly run (configurable). If the budget is exceeded mid-run, distillation stops and the remaining notes are deferred to the next week.
Progressive levelsLevel 1 → Level 2 (gist, Gemini Flash) → Level 3 (summary, Gemini Flash Thinking) → Level 4 (principle, Gemini Pro). Each level is a separate Gemini call. The summaries are written to the Note object (l2_summary, l3_summary, l4_summary).
AuditEach distillation run emits an observability event: notes processed, tokens used, levels produced, any errors. The PM can see the distillation history in the dashboard.
Skipped weeksIf the weekly budget is exceeded or Gemini is unavailable, the distillation is skipped. The PM is notified. The notes remain at Level 1 until the next successful distillation.

Tight budgets vs. loose budgetsTight budgets — low token limits, frequent circuit breaker triggers, PM constantly adjusting budgetsLoose budgets — high token limits, rare circuit breaker triggers, PM rarely thinks about costMiddle — moderate budgets with observabilityTight budgets frustrate the PM and trigger circuit breakers too often. Loose budgets lead to cost surprises. The right approach is moderate budgets (session 200K, weekly 500K — enough for a productive session but not unlimited) with strong observability (the PM sees what the system costs in real time and can adjust). The PM sets the budgets; the system enforces them.
Feature breadth vs. feature depthBuild many features (all 12 agents, all endpoints, vector store, graph store, integrations, enterprise features) — a broad but shallow productBuild few features deeply (Phase 1 coaching loop done really well, governance layer done really well, documentation done really well) — a narrow but deep productOption B (depth over breadth)A narrow, deep product that works beautifully is more valuable than a broad, shallow product that works marginally. Phase 1 + governance layer + documentation is the deep focus. The other features (Phase 2-4) are planned but not urgent. Depth first, breadth later.
Build governance layer now vs. laterBuild governance layer (S1-S5) now, before or alongside Phase 1 — the coaching loop has governance from day oneBuild governance layer later — focus on Phase 1 first, add governance when the coaching loop is stable and the PM is using it regularlyMiddle — S1 (observability) now, S2-S5 after Phase 1 is stableObservability (S1) is essential from day one — you need to see what the agents are doing and costing before you can govern them. Budgets + circuit breakers (S2) are important but can follow Phase 1 — the deterministic fallback ensures the product works even without budget enforcement. Human gate + cache (S3) and distillation (S4) can follow. The governance layer is built incrementally, not all at once.
Single-user vs. multi-user from the startBuild for multi-user from the start — RBAC, team workspaces, shared knowledge layer, team observabilityBuild for single-user first — one PM, one workspace, one knowledge layer — and add multi-user laterOption B (single-user first)Single-user is simpler, faster to build, and validates the core value proposition (does PolyVerses help one PM?). Multi-user adds complexity (RBAC, shared state, team observability, conflict resolution) that is not needed until the product is validated and adopted by teams. The architecture supports multi-user (Firestore security rules, user-scoped data, settings per user) — it's a future enhancement, not a day-one requirement.

26.6 Incident Management

AspectApproach
Incident definitionAn incident is any event that disrupts the product's functionality or usability for the PM — API outage (Gemini down), Firestore issue, bug that blocks a core flow (plan generation fails, workout logging broken), security issue (auth bypass, data leak).
DetectionThe PM notices the issue (manual use of the product), or the observability dashboard flags an anomaly (circuit breaker triggered, Gemini error rate spike, budget exceeded). Future: automated alerts (Sentry, external monitoring).
Response1. Acknowledge the incident (the PM knows it's being addressed). 2. Assess severity (is it a full outage, a partial issue, a minor bug?). 3. Mitigate (fallback to deterministic logic if AI is down, disable the feature if it's broken, roll back if a recent change caused it). 4. Fix (root cause fix, not just mitigation). 5. Verify (the fix works, no regressions). 6. Communicate (update the PM, update release notes / status if public).
Post-mortemFor significant incidents, write a post-mortem: what happened, what was the impact, what was the root cause, how was it fixed, what can be done to prevent it in the future. Store in the decision log or a retro note.
Incident logMaintain an incident log (Firestore or markdown) — date, severity, description, impact, root cause, fix, post-mortem link. This is part of the governance/audit trail.

28.5 Knowledge Base Index — Agent Run Metadata

Agent run logs are stored in the agent_runs Firestore collection. Each run captures:

interface AgentRun {
  id: string;
  agentId: string;           // F00-F11
  modelTier: 'flash' | 'flash-thinking' | 'pro';
  inputTokens: number;
  outputTokens: number;
  durationMs: number;
  intent: string;            // What the agent was asked to do
  outcome: string;           // What the agent produced (summary)
  decisionGateTriggered: boolean;
  timestamp: string;         // ISO 8601
  userId: string;            // Firebase Auth UID
}

This data is queryable via /api/observability and visualized in the Observability Dashboard. It is the project's operational memory — what the agents did, what they cost, what decisions were made.
